- (direction by user) Goal: replace the messy spreadsheet — not a commercial product pitch
- (decision) Stance: Creative Partner; techniques chosen by facilitator
- (technique) started Job to be Done (structured)
- (insight by user) Current state: test cases are PRINTED ON PAPER — testers manually tick pass/fail and write comments by hand
- (insight by user) Ticked paper sheets get submitted directly to the developer — developer is the consumer of the artifact
- (insight by user) Developer's job: extract failures from paper, prioritize them, fix one by one
- (insight by user) Re-test = full reprint, test from scratch; 'test conducted date' on the sheet is the ONLY history/versioning
- (insight by coach) JTBD synthesis: tool is hired to (1) capture verdicts digitally at moment of testing, (2) report as free byproduct - zero transcription, (3) give each test case a memory across fix/re-test cycles, (4) show developer failures first with comments, (5) kill the reprint
- (technique) switched Job to be Done -> Role Playing (collaborative)
- (insight by user) Workflow: test cases created PER FEATURE, sent to project's developers; developer does his own testing run AND business user does his own testing run too - same cases, separate testers
- (idea by user) New-system flow: business user runs tests + generates report -> developer views report/issues -> developer can ALSO run the same cases to reproduce/locate the issue -> fixes one by one
- (idea by user) After fix: business user re-runs - choice of FULL suite (regression) or FAILED-ONLY (targeted retest)
- (idea by coach) Third status 'Reproduced' for developer runs - tells business user the report was heard
- (technique) switched Role Playing -> How Might We (structured)
- (direction by user) User wants to converge now: turn session into a PRD brief and continue from there
- (technique) switched How Might We -> Converge (MoSCoW scoping)
- (decision) MoSCoW locked: MUST = 4 roles/permissions, suites per feature, tick pass-fail+comment per runner, auto-generated report submitted to devs, failures-first view, re-run full-or-failed-only, status history per case; SHOULD = Reproduced status, fix-progress visibility, feature done-declaration; COULD = safe mid-run edits, disagreement flag, admin dashboard; WON'T = CI hooks, mobile apps, SaaS billing
- (insight by coach) Synthesis connections: (1) status-history, re-run buttons, and failures-first are three VIEWS of one run-log table (case x runner x round); (2) 'Reproduced' turns the report from a message into a conversation - the product's real unit is the CYCLE (run->report->reproduce->fix->re-run), report is the midpoint not the end; (3) the tick screen IS the product - everything else is a view of the ticks; (4) project membership = permission boundary for reports
- (decision by user) Open question resolved: BUSINESS USER declares 'testing done' for a feature
- (decision by user) Open question resolved: mid-run test-case edits require ADMIN APPROVAL before taking effect
